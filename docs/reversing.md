# 역분석 기록

분석일: 2026-10-15. 원본 바이너리와 리소스는 변경하지 않았다. 원작 소스가 없는 상황에서 디스어셈블과 데이터 해독으로 이식 범위를 좁혔다.

## 기준 파일

| 파일 | SHA-256 |
|---|---|
| SHIN.EXE | `f358e1b58032575dbb1f6ece2e557f04e631f5dd6307c5097ec34fe9bbbcdd98` |
| RESOURCE.RES | `060da8d3c80654d35027d077a7f9c9c29c5878aa03b4b1dcb5ce991663b3e1ba` |

SHIN.EXE는 PE32 x86, 이미지 베이스 `0x400000`, 엔트리 `0x450ab0`. `.text` 가상 주소 `0x401000`, 파일 오프셋 `0x400`. `.data` 가상 주소 `0x45a000`, 파일 오프셋 `0x58000`. 직접 import는 KERNEL32, USER32, DDRAW, DSOUND, WINMM이다. 함수 이름은 분석을 위해 붙인 것이며 원래 심볼이 아니다.

예시 디스어셈블 명령(macOS의 LLVM objdump):

```sh
objdump -d --no-show-raw-insn --x86-asm-syntax=intel \
  --start-address=0x405cf0 --stop-address=0x406f40 'Changoo (E)/SHIN.EXE'
```

코드 영역에도 점프 테이블이 들어 있으므로 선형 디스어셈블의 모든 줄이 명령어인 것은 아니다.

## 리소스 형식

모든 수치는 little-endian이다.

| 형식 | 구조 | 검증 |
|---|---|---|
| RES | `u32 count`, 항목당 `char name[20], u32 offset, u32 length` | 1,052개, 디렉터리 끝 29,460, 모든 범위 유효 |
| APP | `u32 width, u32 height, u32 payloadLength`, 이후 `(u8 color, u8 count)` 반복 | 1,038개 전부 count 합계 = width × height |
| PAL | RGB 순서의 256 × 3바이트 | 각 채널을 `<< 2`, 254번은 스프라이트 투명색 |
| MAP | `u32 width, u32 height`, 이후 행 우선으로 10바이트 셀 | 7개 모두 `8 + width × height × 10` |
| MAP cell | `i16 decoration, i16 terrain, i16 object, i16 dx, i16 dy` | 미사용 인덱스는 -1, 오프셋은 부호 있음 |

맵 목록: stage1 1059×100, stage2 1401×100, shoot 1400×20, stage3 1131×100, stage4 999×200, stage5 1407×100, stage6 1402×100.

APP 디코더 `0x4402c0`, 핵심 RLE 루프 `0x440402–0x440426`. 확장자 `.raw`를 리소스의 `.app`로 변환해 읽고, 해제 후에는 width/height 8바이트 뒤에 픽셀을 둔다. 웹은 별도 객체에 픽셀을 저장한다.

팔레트 변환 `0x424a17–0x424a3c`의 RGB 각 `shl 2` 확인. `0x424bd6`에서 컬러키 254 설정. 255까지 선형 보간하지 않는다.

## 맵·렌더링·충돌

- `0x4279a0–0x427ab0`: RES에서 스테이지 맵을 찾아 행 단위로 로드. 원본 메모리 행 피치는 1,500셀(15,000바이트); 파일 피치는 실제 width. 웹은 파일 피치를 그대로 사용한다.
- `0x427c11` 이후: 타일 인덱스 `% 20`, `/ 20`, 각각 `<< 5`로 32×32 픽셀 영역을 선택한다.
- `0x4321f0–0x43225f`: 시각적 타일 `tile1.raw`와 판정용 `block1.raw`를 각각 로드한다. 맵의 앞 두 레이어 모두 시각적 타일 시트를 사용하고, 충돌은 두 번째 레이어의 인덱스만 사용한다.
- `0x424c98`: `gra.raw` 로드. 맵 마지막 15행에 높이 480의 배경 띠 적용, 그 위는 첫 행 색.
- `0x426380–0x42640c`, `0x427610` 및 CHAR.CFG: 오브젝트 종류는 CFG 줄 번호. 좌표는 `tileX*32 + 16 + dx - trunc(spriteWidth/2)`, `(tileY+1)*32 + dy - spriteHeight`.
- `0x431130`: 사각형 경계 8픽셀 간격 및 모서리를 샘플링. 타입 1은 고체, 타입 5는 바닥의 위험 판정. 타입 2/3/4는 후속 스테이지에서 추가 해독 필요. stage1 mask는 0/1/5/254와 비충돌 값 72/94를 포함한다.
- `0x431d60`: 바닥 샘플로 지지 여부 확인. 타입 1~4를 반환하며 5는 지지로 취급하지 않는다.
- `0x40d4df–0x40d5b8`: 고체 충돌 시 y를 0~25픽셀 위로 탐색하고, 실패하면 이전 위치를 향해 x와 y를 순서대로 되감는다. 충돌 뒤 속도를 강제로 0으로 만들지 않는 점까지 이식했다.

## 기본 플레이어

생성 `0x405b10`, 업데이트 `0x405cf0`, 지형 충돌 콜백 `0x40d4c0`. 스프라이트 로드 `0x4059c0`의 20바이트 이름 배열, 프레임 배열은 `.data`에 저장된다.

| +100 | 수평 이동 활성화 플래그 |

| 상태 | 값 | 진입 함수 | 프레임 | 기간 |
|---|---|---|---|---|
| 서기 | 0 | 0x40d730 | stop0 | 100 |
| 걷기 | 1 | 0x40d760 | walk0~3 | 5 |
| 공중 | 2 | 0x40d790 | 상승 jump0, 하강 jump1 | 10 |
| 착지 | 5 | 0x40d7c0 | jump2 | 5 |

- 원본 키 대응: WM_KEYDOWN `0x4339a1`의 점프 테이블에서 Left→`0x46d4b8`, Up→`0x46d4b0`, Right→`0x46d4bc`. Space는 별도 공격/아이템 플래그이므로 웹 점프에 재매핑하지 않았다.
- 수평 입력 `±8` (`0x405f63`, `0x405f7d`) 이후 프레임 말미 마찰 1 (`0x406d79`), 실제 이동량은 지속 입력 시 ±7.
- 점프 `vy=-15` (`0x405d7d`, `0x405f09`). 프레임 말미 중력을 먼저 더해 첫 이동은 -14. 자유 상승 높이 합은 105픽셀.
- `0x406d92`: vy가 10 이하이면 1 증가. 낙하 상한은 **11**.
- 지면에서 벗어날 때 `vy=4`, 이후 중력 적용으로 5.
- 공중에서 바닥 +4픽셀 지지와 양의 vy가 만나면 착지 상태, vy=0, 말미에 1로 증가한다.
- 걷기 애니메이션은 `ticks > 5`일 때 진행하므로 프레임당 6틱.
- `0x44d558`: 맵 오브젝트 90이 만드는 대기 이벤트의 20틱 후 수평 이동 활성화. 기본 시작도 현재 이 이벤트의 실제 생성/20틱 대기를 따른다.
- 원본 생성 좌표는 `0x43f136`의 타일 좌표 ×32. 초기 웹 검증판은 `(0,0)`부터 낙하 500틱을 미리 계산했으나, 아래 진입 연출 복원 이후 기본 시작에서는 제거했다. 개발용 구간 시작 버튼만 지면 사전 계산을 유지한다.

카메라: `0x427eb0` 기본 좌우 기준 170/470, 위아래 240/280. `0x425d11–0x425fbc`의 정수 나눗셈 기반 추적을 옮겼다. 타일 캐시 갱신의 1틱 지연 등은 아직 동등성 검증 대상에 포함하지 않았다.

## 원본 함수와 대조한 검증

`tools/capture-original.py`는 [Unicorn의 Python API](https://www.unicorn-engine.org/docs/tutorial.html)를 분석 도구로만 사용한다. 원본 PE 섹션과 리소스를 격리된 메모리에 올리고 아래 함수를 직접 실행한다. Windows API·파일 I/O·네트워크 호출을 구현하지 않는다. 매 호출에는 실행 시간·명령어 수 제한과 정상 return 확인이 있다.

1. 난수 시드 1997, 첫 스테이지 하부 40행에 걸친 좌표 600개에서 `0x431130` 결과 기록.
2. 시작 (0,3032), 기본 형태·이동 활성화·카메라 y=2719·렌더링 비활성으로 `0x405cf0` 실행.
3. 각 틱마다 원본 `0x431130`, 필요시 `0x40d4c0`로 충돌 해결.
4. 이동·반대 방향·점프·키 해제 시나리오 142틱의 x/y/vx/vy/상태/프레임/틱/점프 키/방향을 기록.
5. Node 테스트에서 웹 로직으로 동일 입력을 실행해 **모든 값 일치** 확인.

기준 결과는 `test/fixtures/original-stage1.json`. fixture를 만들 때 사용한 도구는 unicorn 2.1.4다. 일반 테스트와 브라우저 실행에는 이 패키지가 필요 없다.

검증의 한계: 전체 EXE를 Windows에서 플레이한 비교가 아니다. 기본 이동 상태와 제한된 입력/좌표 표본에 대한 함수 수준의 동등성이다. 원본 창의 그래픽·오디오·프레임 속도·모든 이벤트 실행 순서까지 확인한 것은 아니다.

### 아이템과 점수

- 둘 다 충돌 사각형 `(5,15,26,50)`. 이미지 크기에 맞춰 판정을 임의로 줄이지 않았다.
- 획득 플래그 +3c가 1이면 중복 획득 무시. 공통 카운터 player+70 증가, 초코비는 +74, 캔은 +ec도 증가한다.
- 공통 카운터 `%100 == 0`이면 player+8c(목숨) +1 및 `BONUS.WAV`.
- `0x43c0a0`, `0x414820`: 동료 UI의 화면 위치 +40에서 획득 연출 시작. 기본 UI 위치 `(10,400)`이므로 연출은 `(50,440)`, vy=-15. `screenY += vy` 후 중력을 적용하고 480을 넘으면 삭제한다.
- 효과음은 각각 `SE6.WAV`, `CAN.WAV`. 원본의 두 사운드 버퍼 교대 재생에 맞춰 웹도 파일별 두 Audio 요소를 교대로 사용한다.

### 적과 상호작용

- 세 적 모두 76×72 이미지, 판정 `(28,14,46,71)`. 초기 상태는 왼쪽 이동. 속도 ±2를 설정한 후 마찰 1로 실제 이동은 ±1.
- 맵 kind 13/14/15는 보이지 않는 15×15 방향 표식. `0x44abb0`으로 만들고 적 콜백 `0x403c30`, `0x446140`, `0x439180`에서 정지/왼쪽/오른쪽 상태로 전환한다.
- c2는 타이머 100, c3는 0에서 시작. 타이머가 정확히 200일 때 공격 상태로 전환한다. 공격 프레임 0의 틱 1에 플레이어 방향을 선택, 프레임 2의 틱 9에 발사한 뒤 이전 상태로 돌아간다.
- c2 공: `vx=trunc((player.x-enemy.x)/32)`, 8보다 크면 7, -8보다 작으면 -7, `vy=-16`. c3 직선탄: 방향에 따라 vx=±4, vy=0.
- 기본 플레이어가 하강 중이고 `player.y+14 < enemy.y+14-20`이면 밟기 처치, player.vy=-15, 점수 +1. 옆면/상승 중 접촉은 피격이다. 피격 상태 또는 무적 시간에는 재피격을 무시한다.
- 피격 상태 4의 애니메이션 `damage0/1`, 밀림 vx=±16, vy=-5. 프레임 1의 틱 4에서 목숨을 감소시키고 100틱 무적을 설정한다. 해당 틱 말미 감소로 다음 상태값은 99. 렌더링은 원본처럼 무적 카운터 %5가 0일 때만 한다.
- 사운드: c1 처치 `DEM-BOY.WAV`, c2 `DEM-H2.WAV`, c3 `PUNCH2.WAV`, 플레이어 피격 `DEM-SHIN.WAV`.

### 원본 대조와 통합 범위

`tools/capture-objects.py`는 공통 PE/RES 로더를 재사용한다. 원본 생성자와 AI·접촉·지형 함수를 실행하며 메모리 할당 함수 `0x42a170`과 DirectSound Play 반환만 분석 환경으로 대체했다. 실제 오디오 출력과 게임오버 연출은 이 검증에 포함하지 않는다.

`test/fixtures/original-objects.json`에 적 780틱, 접촉 16조건(중복 호출 포함), 피격 회복 30틱, 표식 9조건, 투사체 220틱, 적 처치 56틱, 획득 연출 72틱을 기록했다. Node 테스트에서 각각 일치한다. 일반 게임 실행은 이 도구나 CPU 에뮬레이터를 사용하지 않는다.

원본 디스패처는 우선순위 `0,1,2,3,4,5,7,6,8,9`, 같은 그룹은 생성 순서대로 실행한다(`0x44d300`, `0x44d3a0`). 이후 실제 스케줄러 실행으로 확인한 배우 우선순위는 적/이벤트/동료 6, 플레이어/흰둥이 8, 지형/접촉 관리자 9다. 지형 보정은 개별 갱신에서 분리해 모든 이동과 흰둥이 갱신 뒤에 실행한다. 세부 검증 범위와 남은 카메라/메뉴 사항은 아래 스케줄러 절에 기록했다.

- 스프링의 상승량은 -34부터 시작하는 중력 적분으로 595픽셀. 원본의 실제 벽 통과 입력에서 `(3480,2969)`부터 최고 y=2374를 거쳐 `(3816,2680)`에 착지한다.

## 닭·바퀴벌레 변신과 기본 플레이어 대기 동작

MAP kind 11(`ichi.app`) → 실제 타입 0x52 → `0x40a210` → `0x40d890`, kind 12(`iroa.app`) → 타입 0x56 → `0x40a285` → `0x40d950`. 둘 다 접촉 시 해당 상태로 바꾸고 아이템 노드를 삭제한다. 점수·목숨·일반 획득 카운터는 증가하지 않는다. 아이콘/스프라이트를 직접 해독해 닭과 바퀴벌레 형태임을 확인했다.

- 닭 공중 상태 `0x406628`: 공중 진입 시 +68(날갯짓 래치), +6c(체공 틱)을 0으로 초기화. 매 틱 +6c 증가 후 Space가 새로 눌리면 `vy=min(0,trunc(flightTicks/40)-8)`. 말미 중력은 기존과 동일. 버튼을 계속 누르는 동안에는 다시 적용하지 않고, 한 번의 비행이 길어지면 상승력이 약해진다.
- 닭/바퀴벌레의 공중 착지는 바닥 지지 외에 좌우 샘플의 비충돌 조건도 확인한다(`0x431f90`, `0x4320c0`). 이동 발판 지지는 별도로 인정한다. 닭 착지는 vy를 0으로 만들지 않으며 바퀴벌레는 0으로 만든다.
- 바퀴벌레 돌진 `0x406c05`: 진행 방향으로 vx=±16, 마찰 적용 후 이동량 ±15. +c4가 20이면 회복 상태로 옮기고 카운터를 0으로 만든다. 회복 상태 +104가 40에 도달하면 대기 상태 복귀. 허공으로 나가면 공중 상태로 전환한다.
- 적 충돌의 상태 17 분기는 하강 여부와 무관하게 처치·점수 +1. 상태 10/14는 일반 공중 상태 2와 같은 밟기 조건. 피격 상태 4를 거치면 일반 대기 상태 0으로 돌아가 변신이 해제된다.
- 일반 대기 틱 99에서 상태 6→11→0 대기 연출. 바퀴벌레 대기는 12→16→12. 이들 전용 대기 연출 중의 점프 래치 처리도 원본 분기를 유지했다.

`tools/capture-forms.py` / `original-forms.json`: 8개 입력 시나리오 1,486틱(벽 옆 착지 포함), 변신 획득 2건, 변신 중 적 접촉 36조건. 좌표·속도·상태·프레임·카운터·입력 래치뿐 아니라 **원본 이미지 파일명**까지 비교했다. 전체 테스트 32개 통과.

통합 경로는 기존 첫 적 검증 위치 `(6288,3032)`에서 시작해 적을 밟고, `(6691,3040)` 스프링으로 도약한 뒤 이동 발판에 착지하고 왼쪽으로 점프해 실제 `(6414,2800)` 아이템을 획득한다. 직접 상태를 부여하거나 아이템을 옮기지 않는다. 브라우저에서도 같은 경로의 획득, 바퀴벌레 스프라이트와 HUD, Space 돌진을 확인했다. [변신 화면](screenshots/stage1-roach.jpg). 닭 형태의 브라우저 실제 조작은 별도 확인이 남아 있다.

## 첫 높은 벽 다음 대화 이벤트 (웹 연결 완료)

kind 65 / ev1_2의 생성 `0x428750`은 32픽셀 폭·위아래 320픽셀 영역을 등록한다. 플레이어 접촉 `0x428820`이 이벤트 `0x443cd0`을 생성한다. 이벤트는 한 번만 생성되며, `0x40e8a0`이 플레이어 업데이트 콜백을 연출용 `0x40e770`으로 교체한다. NPC 3명 생성자는 `0x44eda0`, `0x428dd0`, `0x42e460`이다.

`tools/capture-event65.py`가 원본 제어 함수 `0x443e30`의 시간 경계와 Enter 건너뛰기, 정리 함수와 등장인물 갱신을 직접 실행해 `original-event65.json`에 기록했다. 그래픽 로더/해제·메모리 할당·GetTickCount·DirectSound 출력은 분석 환경으로 대체한다. 웹 구현은 `web/events.js`, 통합 연결은 `stepWorld`에 있다. **이 대조는 원작 Windows 전체 화면과 실시간 오디오를 검증한 것은 아니다.**

시작 효과음은 29.WAV와 30.WAV. 다음 시각은 `>` 비교(동일 시각에는 아직 전환하지 않음)이다:

전환 사이에 29/30.WAV도 반복 재생되므로 fixture의 sounds 배열 순서를 사용한다. Enter는 누른 상태를 래치에 기록하고 **뗀 뒤** NPC 상태 정리와 일반 플레이어 콜백 복귀를 수행한다. 정확히 경계/경계+1인 18개 검사와 눌림/해제 검사가 통과했다.

플레이어 연출 `0x40e770`은 상태 20에서 마찰 후 매 틱 x+1, 나머지 상태 21~25에서는 vx=0이다. 중력·지형 보정은 계속 적용한다. 원본 이름 테이블 `0x45d2f8`, 프레임 배열 `0x45d3e8`에서 walk0~3 및 1#241~248을 선택한다. 상태 21~25는 화면 y-9에 그리며 방향 반전을 하지 않는다. 6자세 총 300틱의 좌표·속도·애니메이션·파일명이 일치했다.

NPC는 camera.x+640/+720/+800, player.y-30에 생성한다. 이미지 이름 테이블은 `0x471d10`(1#211~214), `0x461e20`(1#221~224), `0x46cc30`(1#231~233). 갱신 `0x44eea0`/`0x428ed0`/`0x42e560`, 지형 콜백 `0x44f040`/`0x429070`/`0x42e700`의 480틱이 웹과 일치했다. 대화가 끝나도 NPC는 남으며 카메라 중심에서 960픽셀을 벗어나면 제거된다.

정리 함수 `0x444170`은 저장한 상태 번호를 복원한다. 종료 제어는 먼저 대기 애니메이션을 설치하지만, 같은 틱에 플레이어가 다시 갱신된 후 정리가 실행되므로 입력에 따라 걷기 등으로 이미 바뀌었을 수 있다. `animationOverride`는 정리 시점의 실제 애니메이션·프레임 수·주기를 보존하며 다음 상태 진입에서 해제한다. 일반/바퀴벌레 공중 갱신은 원본처럼 상승/하강 때 그림 테이블을 갱신한다. 기존 정리 함수 5상태와 아래 전체 스케줄러 대조를 모두 통과했다.

웹 시계는 일시정지 시간을 제외한 실제 경과 시간을 사용한다. 대사 파일은 미리 로딩하고 정지/재개 시 오디오도 함께 제어하며, 건너뛰기/재시작 시 관련 재생을 정리한다. 브라우저에서 집 앞 정상 경로 → 이벤트 진입 → NPC 3명·짱구 자세 → 정지/재개 → Enter → 오른쪽 이동(X=4518)까지 확인했다. 최종 코드로 다시 진입해 대화를 끝까지 진행한 뒤 자동 종료와 오른쪽 이동(X=4413)도 확인했다. 브라우저 오류/경고 없음, 전체 테스트 39개·구문 검사 통과. [이벤트 화면](screenshots/stage1-dialogue.jpg). 원본 Windows 출력과의 음성 동기/프레임 속도 및 게임 전체 갱신 순서는 별도 검증 범위다.

## 초코비 연출 (kind 118, 웹 연결 완료)

생성 `0x4363c0`, 접촉 `0x436520`의 영역은 (-50,-320,32,320)이다. 한번 접촉하면 `0x40e660`이 업데이트를 `0x40e270`으로 교체한다. 상태 번호는 유지하고 프레임/틱 및 두 회상 애니메이션 카운터를 0으로 만든다. 그래픽/오디오 초기화는 `0x40dfb0`, 해제는 `0x40e5e0`이다.

이미지 이름 `0x45ca60`(39개), 프레임 인덱스 `0x45cd70`(51개), 프레임 유지시간 `0x45ce40`(51개)을 읽는다. 한 갱신에서 최대 한 단계만 전환하며 `elapsed > duration`일 때 기준 시각을 현재 시각으로 바꾼다. vx는 기존 값에서 마찰로 줄고 중력·지형 보정은 유지된다. 프레임 37/41/44/46/48/49의 첫 틱에서 21~26.WAV를 재생한다. 프레임 50의 첫 틱에 cho 소품을 제거하고, 51에 도달하면 프레임 0과 일반 업데이트로 복귀한다.

프레임 47에서는 recall.app을 (player.x, player.y-180)에, rc_m1~4를 (x+78,y-182), rc_s1~5를 (x+16,y-88)에 추가로 그린다. 두 애니메이션은 각각 20틱마다 byte table `0x45cf60`=[0,1,2,3,2,0], `0x45cfd0`=[0,1,2,3,4,0]을 따라간다. 인덱스 5에서 완료 플래그를 세우지만 **카운터는 멈추지 않는다**. 30Hz 기준 카운터 7까지 증가하며 6/7은 실제 원본의 0 패딩을 읽는다. 웹도 이를 반영했다. 더 빠른 틱에서 인접 메모리까지 읽는 원작 화면은 속도 보정 때 재확인해야 한다. 원본은 Enter를 뗄 때 일반 업데이트로 복귀하지만 그 틱의 연출 계산을 끝까지 수행하며, 일찍 건너뛰면 cho 소품이 남는다.

`capture-event118.py`는 30Hz 입력 시계로 원본 업데이트 1,210틱, 음성 6회 순서, 두 회상 애니메이션 완료와 Enter 건너뛰기를 실행해 `original-event118.json`을 만들었다. 그래픽 초기화/해제는 생략하고 오디오 초기화와 시계 값을 분석 환경에 제공한다. `web/intro.js`가 표와 업데이트를 이식하고 `stepWorld`가 실제 kind 118 접촉을 연결한다. 원본 좌표·속도·상태·프레임·틱·음성·회상 카운터·제거 상태가 모두 대조됐다.

브라우저에서 X=693에 연출 진입, 캐릭터 동작·회상 말풍선·소품 줍기·일시정지/재개·자동 종료 및 소품 제거를 확인했다. 종료 후 X=811로 이동, 새 실행에서 Enter 건너뛰기 후 소품을 남긴 채 X=819로 이동했다. [초코비 연출 화면](screenshots/stage1-chocobi-scene.jpg). 전체 테스트 47개·구문 검사 통과, 브라우저 오류/경고 없음.

후반 Enter 해제는 프레임 번호를 0으로 정리하지 않아 일반 스프라이트 배열 밖을 참조할 수 있다. 웹은 프레임 카운터를 유지하되 표시할 그림이 없으면 stop0을 사용하며, 다음 일반 애니메이션 갱신에서는 원본처럼 0으로 되돌린다. 이 순간의 실제 Windows 화면 대조가 남아 있으므로 완전한 픽셀 재현으로 보지 않는다.

## 공·물폭탄과 선택 메뉴 (웹 연결 완료)

맵 kind 43/44는 타입 0x47/0x48 아이템이며 획득 콜백 `0x409e66`/`0x409eb1`이 점수와 플레이어 +0xe0/+0xe4 탄약을 1씩 올린다. kind 43 생성 `0x44dbf0`, 갱신 `0x44dcc0`, 획득 팝업 `0x44de50`; kind 44 획득 팝업 `0x4242a0`. CHAR.CFG는 둘 다 ball.raw를 사용한다.

일반 플레이어의 지상 Space(`0x46d4e8`)는 +0xe8 래치가 0일 때 선택값 `0x46cd04`가 0/1이면 해당 탄약을 소비하고 투사체를 만든다. 타입 0x41 생성/갱신/접촉/지형은 `0x42d640`/`0x42d730`/`0x42d810`/`0x42e130`, 타입 0x42는 `0x42fc60`/`0x42fd50`/`0x42fe30`/`0x430a50`. 초기 vx=방향×10, vy=-10, 몸체=(2,2,12,12). 선택 UI는 `0x42eff0`/`0x42f060`, Enter 해제 시 `0x42f306`에서 선택값을 저장한다. 2 이상의 선택값은 동료 아이템 호출도 포함하므로 이 메뉴의 전체 제어를 추적해야 한다.

`capture-weapons.py` / `original-weapons.json`이 두 아이템·발사 68시퀀스(476틱)·궤적 4개·적 명중 6조건·범위 효과 충돌 33틱·선택 메뉴 27입력을 직접 실행한다. 대기 지루함 상태 11의 물폭탄은 첫 Space 틱에는 던지지 않고 **누르고 있는 이후 틱마다** 던지는 특이한 분기(`0x40678a`)가 있어 동일하게 구현했다. 일반/이동/둘러보기 상태에서는 새 입력에 한 번만 던진다. 다른 변신/공중/착지 상태의 발사 제한도 대조했다.

공은 3회 반사 후 제거, 물폭탄은 첫 충돌 때 제거하고 범위 효과를 생성한다. 반사 처리는 x 보정으로 이미 충돌이 풀려 y 좌표가 변하지 않아도 y 루프가 성공하면 vy를 뒤집고 횟수를 더한다. 단순 좌표 변화 검사로 대체하면 원본과 달라지므로 투사체의 반사 루프를 그대로 이식했다.

범위 효과 `0x42b300`은 충돌 위치에서 (-37,-50)에 boom.app(116×71)을 그린다. 몸체=(14,12,106,70), 갱신 `0x42b3d0`은 11틱째 제거한다. 실제 충돌 디스패처 `0x434a50`로 실행한 결과, 동일한 죽는 적을 재접촉하며 사망 애니메이션을 초기화하고 점수를 추가한다. 3종 모두 시나리오에서 9회 득점했으며 웹도 동일하게 동작한다. 이를 임의로 한 번의 보상으로 바꾸지 않았다.

일반 플레이어 Enter 해제는 `0x406dfa` 이후 선택 메뉴를 생성하고 게임 갱신 그룹을 멈춘다. 메뉴는 0~7 커서를 위/아래 키 새 입력에 한 칸씩 움직이며 경계에서 멈춘다. Enter 해제 시 선택을 먼저 확정한 뒤 같은 틱의 방향 입력도 처리한다. 기존 화면 위에 arrow.app을 (60,100+40×커서), 각 소지품을 (100+10×개수인덱스,100+40×행)에 쌓아 그린다. 이미지 목록은 `0x46cd08`의 ball/wbomb/item_m/item_f/item_si/item_ym/item_fr/item_w이다. 뒤 6칸의 소환은 아래 동료 절에서 연결했다.

첫 스테이지에는 kind 43/44 배치가 없다. 개발용 공격 위치는 stage2.map의 실제 (4600,888) 물폭탄 위쪽 (4540,800)에서 시작한다. 원래 아이템 위치를 바꾸거나 탄약을 지급하지 않는다. → 25틱으로 획득, (4717,1464) 착지, Enter/↓/Enter 선택 후 Space 발사와 벽의 범위 효과를 테스트 및 브라우저로 확인했다. ## 원본 스케줄러를 통한 결합 검증

`capture-world.py`는 원본 `0x44d3a0`을 실행한다. 지형 관리자 `0x430fd0`/`0x431000`과 접촉 관리자 `0x434a20`/`0x434a50`도 원본 그대로 등록한다. 생성 코드 `0x43f120`은 플레이어와 흰둥이를 우선순위 8에, 두 충돌 관리자를 9에 등록한다. 지형 관리자가 접촉 관리자보다 먼저 생성된다.

초기 그래픽 대체 로더는 APP 헤더만 제공했으나 지형 관리자 생성자가 block1을 다시 로드한다는 점을 확인했다. `capture-graphics-support.py`는 block 파일에 한해 실제 RLE 픽셀을 해독한다. 이 수정 전에 만들어진 실패 실행 결과는 기준 데이터로 저장하지 않았다.

`original-world.json`은 전투 220틱, 대화 전체와 조작 복귀 1,220틱, 움직이는 플레이어/적과 아빠·흰둥이 520틱을 포함한다. 좌표·속도·상태·프레임·주기·그림 파일·피격/점수·동료 위치를 대조했다. 대화 전환 프레임의 불필요한 x+1, 아빠가 갱신 후 플레이어 위치를 먼저 따라가던 차이, 제거 예정 적을 흰둥이 표적에서 한 틱 빨리 제외하던 차이를 수정했다.

웹은 적/이벤트/동료 → 플레이어/흰둥이 → 지형 → 접촉 → 정리 순서로 실행한다. 일반 플레이어의 이전 좌표는 갱신 시 기록하며, 연출 전용 콜백은 원본처럼 그 필드를 다시 쓰지 않는다. 방향 표식도 화면 셀에 나타날 때 활성화하고 새 객체의 접촉 대기를 지킨다. 이 결합 검증은 **고정 카메라**와 지정한 배우 구성이며, 원본 카메라·그림 출력 순서, 메뉴 중 관리자 실행, 모든 객체 조합까지 증명하지는 않는다.

## 첫 보스와 다음 스테이지

kind 18 / type 0x74는 단순 인물이 아니라 체력 10의 첫 보스다. 생성 `0x421f90`, 갱신 `0x4220a0`, 지형 `0x4224b0`, 방향 표식 접촉 `0x422470`. 원본 이미지 ryoko_s/w1~w4/d/a1/a2, 크기 146×177, 몸체=(48,6,100,176)이다. 보스 이름 그림 ryoko_h를 (10,50), rlife를 (50+20×인덱스,50)에 표시한다.

상태 1/2는 좌/우 걷기(마찰 후 ±1), timer>200이면 상태 3 돌진으로 바뀐다. 돌진 첫 프레임 tick=1에서 플레이어 방향으로 vx=±10을 설정하고 이후 마찰로 줄인다. 프레임 5/tick 9에 다시 플레이어 방향으로 걷는다. `0x422680`은 체력을 1 줄이고 상태 4로 전환하며 PUNCH2.WAV를 재생한다. 체력이 남으면 tick 9에 다시 돌진, 체력이 정확히 0이면 첫 틱에 vy=-10, tick 9에 제거·맵 전환을 요청한다.

## 두 번째 보스·종료 화면·슈팅 이동/발사

소품 그림은 gamecar.app(73×102), gamech_b.app(58×104)이지만 두 접촉 영역은 (0,0,79,91)이다. 접촉하면 소품을 제거하고 우선순위 2/6/7/8을 끈 뒤 5에서 미니게임을 실행한다. 종료는 해당 그룹을 다시 켜고 스테이지 카메라 +0x2c를 0으로 만든다. 성공·실패가 메인 플레이어의 목숨/점수/소지품을 변경하는 보상은 없다. 웹은 소품 활성화·접촉·소모와 부모 상태 보존을 연결했다. **원본 priority 9 지형/접촉 관리자는 모달 중에도 실행되므로 현재 부모 월드 전체 정지와의 경계 차이는 후속 통합 대조 대상**이다.

자동차의 200×8 LE u32 장애물 표는 0x45a228이다. 500ms를 초과하면 행을 넘기고 배경/차 그림 2장을 번갈아 출력한다. 충돌은 현재 행+1, 입력은 렌더링 뒤에 받으며 좌우 새 누름마다 차선 1칸을 변경한다. 차선 범위 보정은 다음 틱이다. 충돌 후 CAR.WAV 루프와 CRASH.WAV를 유지하고 2,000ms 초과 후 종료한다. 원본은 진입 및 46초 초과마다 CD 오디오 13~14번 범위를 요청한다. ISO 디렉터리 479파일을 읽어 확인한 현재 CD 이미지는 전체 61,954,048바이트가 ISO 9660 데이터 영역이며 별도 CDDA 트랙/큐 시트는 없다. 웹은 WAV를 재생하며 CD 음악은 아직 제공할 수 없다.

원본 표의 180~199행은 8개 차선이 모두 1이다. 일반 입력으로 최대 생존하는 경로도 이 벽에서 충돌한다. 성공 조건은 row>192이며 표를 바꾸거나 무적 처리를 추가하지 않았다. 성공 분기 검증만 초기 row=192/stepAt=1로 설정한 독립 경계 테스트다. 실제 입력으로 성공했다는 의미가 아니다.

깃발의 3라운드×30명령×4필드 표는 0x45f9f8부터 각 라운드 480바이트다. 필드는 음성 인덱스/응답 시간/정답 자세/명령 간격. 원본은 모든 라운드에서 첫 라운드의 간격과 정답 열을 사용하며 음성과 응답 시간만 라운드별이다. 자세 0 청 올림=→, 1 청 내림=↓, 2 중립, 3 백 올림=↑, 4 백 내림=←. 이전 틱의 자세와 시각으로 판정하고 화면을 그린 뒤 현재 입력을 받는다. 동시 입력 우선순위는 ↑→왼쪽→오른쪽→↓ 순서다. 중립 정답은 입력 없이 제한 시간까지 기다려야 한다. 정답 EAT.WAV, 오답 FAIL.WAV, 내부 기회 5개이며 모두 소진하거나 3라운드를 끝내면 복귀한다. 라운드 사이 안내는 2초다. inputActive 초기화가 그림 출력 분기 안에 있으므로 원본 대조에서도 렌더 분기를 켰다.

원본 `RESOURCE/game.dat`는 20바이트의 5개 LE u32 해금 플래그이며 현재 값은 [1,0,1,1,0]이다. 미니게임 생성 때 해금하므로 승리 조건이 아니다. 웹은 이 값을 최초 초기값으로 읽고 `changoo.minigame-unlocks.v1` localStorage에 저장한다. 유효한 브라우저 기록이 있으면 원본 초기값보다 우선한다. 길이/값 검증, 손상 JSON의 초기값 복귀, 저장 차단/용량 오류의 실패 반환을 테스트했다. 원본 파일은 수정하지 않으며 `save.dat` 최고 스테이지 및 원작 저장 메뉴와는 별도다.

`tools/capture-minigames.py`는 실제 생성·갱신·정리 함수를 실행하고 DirectDraw 표면/팔레트, 시계, CD 명령, game.dat 파일 I/O만 분석 환경으로 대체한다. 자동차 무입력 174틱·최대 생존 2,926틱·성공 경계 2틱, 깃발 무입력 411틱·3라운드 성공 5,502틱, 총 9,015틱의 모든 상태/음성/CD 요청과 표본 그림을 비교했다. 원본 표와 리소스 이름은 `web/minigame-data.js`로 추출했다. 브라우저에 CPU 에뮬레이터는 들어가지 않는다.

## 슈팅 보스·대화와 부스터 구간 전환

보스 kind 33의 실제 위치는 `(38262,187)`이며, 로더 `0x436f10`, 생성 `0x4370f0`, 갱신 `0x437200`, 정리 `0x437620`이다. node type 0x6b, 논리 크기 179×204, 접촉 영역 `(38,10,113,189)`, 초기 체력 20. 15장 chh12~chh125 그림, rlife.app과 bsfc31.app을 쓴다. 맵 생성 분기 `0x42674f`는 생성 즉시 `0x461754=1`로 자동 수평 스크롤을 멈춘다.

상태 1은 매 틱 원본 CRT 난수를 두 번 사용해 vx/vy를 -3..3으로 정한다. 수평 마찰 1을 적용하고 수직에는 중력이 없다. timer=20 또는 20초과일 때 공격 상태 3으로 전환한다. 공격은 frame 1/tick 9에 조준탄 37을 생성하고 상태 1로 복귀한다. 피격 상태 4는 **첫 프레임의 21틱 동안 매 틱 조준탄을 발사**하고 다음 프레임 첫 틱(22번째 갱신)에 체력을 1 줄인다. 살아 있으면 공격 상태 3으로, 0이면 즉시 다음 맵 요청으로 끝나며 그 최종 틱의 이동/타이머는 실행하지 않는다. 몸 접촉은 피격 상태도 다시 시작시킬 수 있지만 레이저는 상태 4를 다시 맞히거나 점수/소모를 발생시키지 않는다. 동료 11조건의 첫/중복 접촉도 원본을 대조했다.

카메라 x~x+500과 y=0~480 보정은 상태 처리보다 먼저 적용된다. 상태 1의 난수 갱신 뒤에는 수평 경계를 다시 확인한다. 원본의 y=500 재검사와 앞선 y=480 보정 순서를 그대로 보존했다. 카메라 중심에서 수평 2240/수직 1680을 벗어나면 원본은 해당 배우를 맵에 돌려놓고 제거하며, 돌아오면 새 체력으로 생성한다. 두더지와 보스는 `random.js`의 같은 32비트 난수 함수를 사용하고 월드/맵 전환에서도 세션 시드를 이어간다.

`capture-flight-boss.py`는 난수 시드 1/1997/0xffffffff 각각 600틱, 경계 24조건, 몸 접촉 12시나리오와 레이저 3시나리오의 첫/중복 결과, 20회 지연 피격 440틱을 기록한다. 마지막 한 타격 22틱에서는 원본 `0x427900` 맵 읽기를 실행해 index 2→3, 1131×100 stage3.map, 목숨 5→8, 좌표0/0, 기존 vx=-4/vy=3/무적17 보존, 플레이어 갱신 `0x407380`·접촉 `0x407bf0` 전환을 확인한다. RESOURCE.RES의 파일 전송과 제목/리소스/진입 연출 초기화는 분석 환경으로 대체하되, 초기화의 그룹 정지 플래그와 원본 모드 전환 함수를 적용한다. `capture-map-support.py`는 이 가상 파일 전송을 첫 보스와 공유한다.

추가로 보스와 실제 주변 적 56 두 마리의 배치, 원본 스케줄러·몸/지형 관리자·카메라 추적 분기를 함께 실행했다. 방향/발사 입력만으로 **580틱에 20회 체력 감소를 완료**, 목숨1을 남긴 뒤 보상 +3으로 부스터에 진입하고 점수22를 유지한다. 웹은 각 틱의 플레이어·보스·난수·효과음·전환 상태가 일치한다. 별도 실제 맵 보스 위치 시험도 목숨5에서 시작해 추가 소지품 없이 처치→부스터 연출→이동/발사를 확인했다. **시작점부터 보스까지의 전체 맵 이동을 포함한 시험은 아니다.**

## 보조 맵 생성표와 적 20/21: 앞선 누락 정정

원본에는 **두 개의 맵 생성 함수**가 있다. 일반 생성 `0x426380`은 화면의 열0..20/행0..15를, 보조 생성 `0x427610`은 더 넓은 열−20..40/행−15..30 범위를 처리한다. 앞서 일반 표 `0x427408`의 반환 분기만 보고 20/21/121/122를 무동작으로 분류했던 해석은 잘못이었다. 보조 표는 바이트 표 `0x427888`와 점프 표 `0x427860`을 사용해 **13~17,20,21,121,122**를 생성한다. 두 표의 합집합을 기준으로 `IGNORED_KINDS`는 [6,7,8]로 정정했다.

초기 로드는 `0x427e41`의 보조 사각형 순회 후 일반 사각형을 순회한다. 화면이 오른쪽/왼쪽/아래/위 타일 경계를 넘을 때는 `0x42531b`/`0x42555e`/`0x4257af`/`0x425a6e`에서 새 외곽만 읽는다. 보조 생성은 절대 열/행이 0 이하이거나 맵 크기 이상이면 반환한다. 생성한 셀의 kind는 −1로 소비한다. 이미 읽은 사각형 안에 다시 놓인 적을 매 틱 재생성하지 않도록 `spawning.js`는 이전 카메라 타일 범위도 기억한다. 방향 표식도 같은 보조 범위에 맞춰 활성화하며 수평2240/수직1680 바깥에서 비활성화한다.

`capture-spawning.py`는 실제 두 디스패처를 실행해 종류별 좌표/소모/맵 경계 54조건, stage2/stage3 초기 및 이동 경계의 생성 기록을 남긴다. 생성자만 관찰용으로 대체하며 좌표 계산과 소비는 원본 명령이다. `spawn-data.js`는 보조 종류 목록이다. 현재 범위 시험은 디스패처와 카메라 호출 지점의 오프셋을 대조한 것이며, **진입 연출 이전의 최초 생성 시점·동시에 여러 경계를 넘는 순서·전체 타일 캐시/렌더 순서까지 입증하지는 않는다.** 이 전체 카메라/스케줄러 대조는 계속 남아 있다.

20/21은 둘 다 143×218이며 원본 chh111/chh112 및 chh211/chh212 그림을 쓴다. 방향 상태1/2는 vx=−2/+2 뒤 마찰1, 정지는 상태0, 처치는 상태4다. 첫 처치 틱 vy=−10, frame1/tick0에서 vy=10/제거하며 최종 틱 갱신도 유지한다. 20은 수평2240/수직1680, 21은 수평960 범위 바깥이면 기존 위치를 맵에 돌려놓고 제거한다. 보조 생성 대상은 가까워질 때 다시 생성된다. 2스테이지에 20번6개/21번4개, 부스터 stage3.map에 20번45개/21번41개가 배치되어 있다. 부스터 첫21번의 원래 좌표는 `(731,127)`, 셀(25,10)으로 화면 밖에서도 미리 생성된다.

일반 플레이어 접촉은 기존 밟기·바퀴벌레 돌진·피격 규칙을 사용한다. 부스터는 접촉 `0x407bf0`에서 상태27/무적을 보호하고 `0x40db40`의 boost5 피격 그림 및 방향별 ±16/-5 반동을 사용한다. 레이저35는 두 적의 처치 상태를 다시 맞히거나 보상하지 않지만 **탄환은 소모**한다. 이는 슈팅 적 55~64와 달라 별도 분기를 유지한다.
